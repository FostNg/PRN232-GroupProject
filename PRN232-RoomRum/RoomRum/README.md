# RoomRum API for `RoomRum_db`

This API targets the 16-table SQL Server schema in [`../Database/DB.sql`](../Database/DB.sql). The project runs with its local `appsettings.json`: ASP.NET Core loads that file automatically; BLL passes `ConnectionStrings:RoomRumConnection` to DAL, while `Program.cs` reads the `Jwt`, `Cors` and `RateLimiting` settings. Copy `appsettings.example.json` to `appsettings.json`, then set the SQL Server address and a private random JWT key. `appsettings.json` is excluded from Git because it contains a database connection string and JWT signing key; provide it locally on each machine. Environment variables such as `ConnectionStrings__RoomRumConnection` and `Jwt__Key` can override individual values. Run `dotnet run --launch-profile RoomRum` from the `RoomRum` directory; the Visual Studio profile opens Swagger at `http://localhost:5041/swagger`. The repository root solution `../RoomRum.slnx` builds this project with BLL and DAL. The root `Setup-GmailSecrets.ps1` and `Start-Gmail.ps1` scripts also target this project.

Build the three-layer solution with `dotnet build RoomRum.slnx`. With the API running locally, `../Database/verify-all.ps1 -BaseUrl http://localhost:5041` exercises all Swagger operations, including permissions, concurrent appointment updates, image ID stability, invitation acceptance, concurrent repeat invitations and paged tenancy history, authentication throttling, Unicode round trips, decimal precision, CORS, inactive accounts, mixed-participant legacy chat data and write flows. It creates temporary records and removes them in a `finally` block. Restart the local API between repeated runs to reset the in-memory authentication rate limiter. Set `-SqlServer` and `-Database` when testing a different SQL Server database. `../Database/verify-api.ps1` is a smaller smoke check and accepts the same SQL target parameters for cleanup. Run the scripts with PowerShell 7 so their UTF-8 literals parse correctly.

Set `Cors:AllowedOrigins` to the exact web origins allowed to call the API. During Development, localhost and 127.0.0.1 origins are also accepted on any port. Tenant registration creates an `Inactive` account and sends an email verification link; `GET /api/auth/verify-email` activates it. `POST /api/auth/send-verification-email` resends a link after a 60-second cooldown when given valid login credentials. Landlords register through `POST /api/auth/register/landlord` with 1-3 property images and 1-2 identity documents; their account is immediately `Active`. Configure `EmailVerification:ApiBaseUrl`, `EmailVerification:TokenMinutes` and SMTP settings before tenant registration. Run the additive [`migrate-registration-verification.sql`](../Database/migrate-registration-verification.sql) against existing databases first. Account login and existing JWTs require the database `User.status` value to be `Active`; an admin can deactivate an account with `{"status":"Inactive"}`.
`RateLimiting:AuthPermitLimit` limits the combined registration and login requests from one remote IP per minute; rejected requests return 429. Deployments with multiple API instances need a shared rate limiter if the limit must apply across instances.

Swagger documents typed JSON success contracts, applicable client errors and a standard JSON envelope for other errors. The three `204 No Content` operations have no success body. Success responses stream through the error middleware; error responses are buffered up to 64 KB for envelope conversion.

List endpoints accept `page` and `pageSize` query parameters. They return an array for the requested page (default 1 and 50 records, maximum 100); request the next page until the returned array is shorter than `pageSize`. Invalid page values return 400. Room search and tenancy history retain their paged response objects with a total count.

`GET /api/rooms` includes the advanced price, area, amenity, monthly cost, distance and sorting filters from Huy's branch; see [advanced search](../Database/ADVANCED-SEARCH.md). `/api/locations/search` and `/api/locations/suggest` resolve Vietnam place names through the configured Photon-compatible service. Coordinates submitted with room create/update are stored in `Room`; changing an address without new coordinates clears the old point. Owners can invite an active Tenant by email with `POST /api/room-tenants/{roomId}/invite-by-email`. Landlords and admins can upload JPEG, PNG or WebP room images of at most 5 MB through `POST /api/rooms/{roomId}/images`.

`../Database/DB.sql` is a **destructive baseline**: it drops and recreates `RoomRum_db`. Do not run it against a populated database. For an existing database created from the supplied script, run `../Database/seed-roles.sql`, `../Database/migrate-user-optional-unique.sql`, `../Database/migrate-unicode-labels.sql`, `../Database/migrate-favorite-unique.sql`, `../Database/migrate-catalog-unique.sql`, then `../Database/migrate-tenant-invitations.sql`, `../Database/migrate-tenant-history.sql`, `../Database/migrate-room-status.sql` and `../Database/migrate-room-coordinates.sql`. Run each migration with `sqlcmd -d <database> -i ../Database/<migration>.sql`; the invitation migration retains existing tenancies and changes the default to `Pending`, while the history migration adds an archive table without deleting current records. The room status migration maps legacy `Draft` to `Pending`, `Deleted` to `Cancelled`, and NULL to `Pending`; apply it to existing databases before using the updated API. The Unicode migration widens user-facing label columns to `NVARCHAR`; the favorite and catalog migrations add unique indexes and stop if duplicate records need review. Email remains optional in SQL, although API registration requires it. `../Database/verify-schema.ps1` compares the live database with the isolated database after the same migrations, including columns, indexes, foreign keys, checks, defaults, primary keys, triggers and collation.

## Layers

| Project | Responsibility |
| --- | --- |
| `RoomRum` (`RoomRum.API`) | HTTP controllers, JWT/CORS/Swagger setup, error envelope and composition root |
| `BLL` (`RoomRum.BLL`) | `DTOs/Requests`, `DTOs/Responses`, `Services/Interfaces` and `Services/Implementations`; business rules and response mapping |
| `DAL` (`RoomRum.DAL`) | `Entities/RoomRumDbContext.cs`, entities, `Repositories/Interfaces` and `Repositories/Implementations`; queries, persistence and transactions |

The dependency direction is API → BLL → DAL. `Program.cs` calls BLL's `AddBusinessServices`; BLL registers its services and calls DAL's `AddDataAccess` to register the context and repositories with scoped lifetimes. Controllers depend on service interfaces. JWT account validation also goes through `IAuthService`. Services depend on repository interfaces and contain no EF queries or SQL operations. DAL owns EF tracking, pagination queries, conditional updates, duplicate-key handling and the tenancy history transaction. DAL does not reference BLL or API. Repository projection selectors keep response mapping in BLL while allowing SQL to select only the necessary columns. DAL classifies storage exceptions, BLL maps them to outcomes, and the API middleware writes the HTTP envelope. See [ARCHITECTURE.md](../../ARCHITECTURE.md).

The application code is organized under `RoomRum/Controllers`, `BLL/DTOs`, `BLL/Services`, `DAL/Entities` and `DAL/Repositories`. API support classes and configuration are files at the root of `RoomRum`; static demo images are under `RoomRum/wwwroot/demo/rooms`, and uploaded image bytes are under the ignored `RoomRum/App_Data/room-images`. The active Visual Studio launch profile is `Properties/launchSettings.json` and uses port 5041. SQL and verification scripts live in `../Database`, outside the three projects. Shared `../Directory.Build.props` redirects build outputs and intermediate files to `../artifacts`, so builds do not create `bin` or `obj` directories inside the projects.

## API groups

| Routes | Database tables |
| --- | --- |
| `/api/auth` | `User`, `Role` |
| `/api/rooms`, `/api/rooms/amenities` | `Room`, `RoomImage`, `RoomAmenity`, `Amenity`, `RoomRating` |
| `/api/rooms/{roomId}/images` | `RoomImage` metadata and local image files |
| `/api/locations` | Photon-compatible geocoder; room coordinates remain in `Room` |
| `/api/appointments` | `Appointment` |
| `/api/favorites` | `Favorite` |
| `/api/sharings` | `Sharing` |
| `/api/rooms/{roomId}/ratings` | `RoomRating`, `RoomTenant` |
| `/api/room-tenants` | `RoomTenant`, `RoomTenantHistory` |
| `/api/reports`, `/api/repairs` | `Report`, `Repairing` |
| `/api/chat` | `Conversation`, `Message` |
| `/api/admin` | `User`, `Role`, `Amenity` |

All IDs in this API are GUIDs. Protected routes require `Authorization: Bearer <token>`. Public registration accepts only `Tenant` and `Landlord`; create the first administrator by registering a normal account, then setting its `role_id` to the `Admin` role and its `status` to `Active` in SQL Server under your own database administration process. Subsequent role changes can use `/api/admin/users/{id}/role`.

Room statuses are `Pending`, `Available`, `Rented`, `Hidden` and `Cancelled`. Room create and update requests have no `status` field and reject it if supplied. New rooms start as `Pending`. An admin lists rooms awaiting review with `GET /api/admin/rooms/pending`, then reviews one with `PATCH /api/admin/rooms/{id}/review` and `{"status":"Available"}` to approve or `{"status":"Cancelled"}` to reject. The owner hides a room with `DELETE /api/rooms/{id}`. Public detail accepts `Rented` and open `Available` rooms. An `Available` room with a pending invitation is visible by ID only to its owner and invited tenant using a JWT; others receive 404. `Pending`, `Hidden` and `Cancelled` return 404. Public search, new appointments and new favorites require `Available` with no pending invitation. A room owner invites a tenant with `POST /api/room-tenants/{roomId}`, which creates a `Pending` tenancy invitation while the room stays `Available`. The invited user accepts with `PATCH /api/room-tenants/{roomId}/accept`; only then is the tenancy record `Active` and the room becomes `Rented`. Either the owner or invitee can cancel a pending invitation with the existing `/end` route. An active tenancy can be ended with the same route. The owner may invite the same user again after `Cancelled` or `Ended`. The closed record is archived in `RoomTenantHistory` in the same transaction that opens the new invitation. The owner and tenant can read paged history with `GET /api/room-tenants/{roomId}/{tenantId}/history?page=1&pageSize=20`. Periods overwritten before the history migration cannot be recovered. Pending or cancelled invitations do not grant rating or sharing privileges.

When the last `Active` tenancy ends, the room returns to `Available` even if other invitations remain `Pending`. A pending invitation hides an `Available` room from public search, detail, ratings and sharing lists until the invitation is accepted or all pending invitations end. If another tenant is still active, the room stays `Rented`.

An admin lists reports awaiting review with `GET /api/reports/pending`, then reviews a report with `PATCH /api/reports/{id}/status` and `{"status":"Resolved"}` or `{"status":"Rejected"}`. Only a `Pending` report can be reviewed.

`GET /api/rooms/mine` shows the owner's `Pending`, `Available` and `Rented` rooms. `PUT /api/rooms/{id}` accepts partial room updates. Supplied nonblank text and non-null numbers replace their current values; omitted, null, or blank values leave them unchanged. Nonempty `amenityIds` replace the amenity list; an omitted or empty list leaves it unchanged. An omitted or empty `imageUrls` list leaves images unchanged. For each URL in a nonempty `imageUrls` list, an existing image with that URL is deleted, while a new URL adds an image. Other images are preserved. An empty object makes no changes.

The active API project compiles its `Controllers` normally. Clients built for the old `/api/Listings` contract must switch to `/api/rooms` and GUID IDs.

The new schema has no tables for payment, notification, refresh token or listing review history, so those old endpoints are unavailable. `RoomImage` stores the image URL; uploaded JPEG, PNG and WebP bytes are kept under the ignored local `RoomRum/App_Data/room-images` directory and served through `/api/rooms/{roomId}/images/{imageId}/content`. Back up that directory together with the database to retain uploaded images. The database has no seed rooms or amenities, so an empty public list is expected until real records are added. JWT access tokens expire after the configured access lifetime; there is no refresh endpoint without persistent refresh-token storage.
